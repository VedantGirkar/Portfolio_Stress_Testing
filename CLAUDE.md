Working rules for Claude in this repository. The detailed module requirements, mandate, workflow, data contracts, milestones, and definition of done are in `PROJECT_SPECIFICATION.md`. Read the relevant sections there before implementing or changing a module.

The specification describes required behavior, not current state. Inspect the repository before deciding what exists. Preserve working code and tests. Do not report a feature as complete without implementing and validating it.

If a requirement is ambiguous, state the ambiguity and ask a focused question before making a consequential financial or architectural assumption.

## Project in brief

A modular Python research platform for a portfolio manager running a stylized financial institution's equity book. It builds a 100-stock sector-diversified shortlist from an S&P 500 snapshot, holds an initial 10-stock portfolio with 90 zero-weight reserves, values holdings and cash in one ledger, measures normal and tail risk, runs historical and hypothetical stress scenarios, proposes cost-aware rebalances (including changes in holding count), maintains a mandatory delta- or gamma-based derivative hedge (method not yet chosen), evaluates everything in a walk-forward backtest, and presents results in a dashboard.

It is a simulated investment-book study: not a live trading system and not a full bank capital, liquidity, or solvency model.

## 1. Non-negotiable requirements

1. Use `uv` as the package and environment manager. Do not introduce pip-based setup instructions, requirements.txt, Poetry, or Conda workflows.
2. Use `.py` files for all implementation, scripts, tests, and application logic. Do not create `.ipynb` files. Markdown documentation, TOML configuration, CSV data, and other necessary non-code artifacts are permitted.
3. Use one standardized repository structure. New modules belong in the existing `src/stress_portfolio/` package, tests in `tests/`, dashboard files in `dashboard/`, and run results in `outputs/runs/`.
4. Do not create a separate mini-project, environment, dependency manifest, app directory, or output tree for each module.
5. Keep the design simple. Prefer clear functions, pandas tables, and a small number of state objects over elaborate frameworks or deep inheritance.
6. Modules must be independently testable and composable.
7. Use a single accounting and execution model throughout the project. No parallel simplified ledger for the dashboard or hedge experiments.
8. Include transaction costs and hedge cash flows. Use configurable constant parameters initially.
9. Derivatives hedging is mandatory for final completion. Delta versus gamma is an explicit later decision gate.
10. Do not add live broker connections or real-money trading.
11. Distinguish implemented functionality, planned functionality, observed data, modeled values, and hypothetical results.
12. Never fabricate a dependency lockfile, market dataset, successful download, passing test, or performance result.

## 3. Testing and uv workflow

Use pytest. Keep core tests offline with small synthetic datasets. Live provider checks must be explicit integration tests, not hidden network calls in ordinary unit tests.

Expected workflow from the repository root:

```bash
uv sync
uv run pytest -q
uv run stress-portfolio --help
```

Add actual dependencies through uv:

```bash
uv add <package>
uv add --dev <test-or-development-package>
```

When the dashboard is implemented and Streamlit is added:

```bash
uv run streamlit run dashboard/app.py
```

Keep `pyproject.toml` and generated `uv.lock` consistent. Do not add every possible library preemptively. Follow the existing Python version unless a documented compatibility issue requires a change.

Every module must have independent tests. Add integration tests at module boundaries and at least one short combined-equity-and-hedge backtest. Test infeasible cases, missing inputs, unavailable options, insufficient funding, and failed optimizations—not only happy paths.

## 4. Financial and research safeguards

- No future information in historical decisions.
- No silent use of present-day fundamentals or membership as point-in-time history.
- No blanket price filling that manufactures returns.
- No hidden capital injection for premium or fees.
- No double-counted dividends, spreads, premium losses, or time decay.
- No claim that VaR bounds worst loss.
- No optimization-success claim based only on in-sample stress improvement.
- No global-optimum claim for heuristic stock selection.
- No guaranteed portfolio floor from a mismatched market hedge.
- No reliance on first-order Greeks alone for severe nonlinear scenario valuation.
- No assumed hedge neutrality without checking residual exposure and constraints.
- No hard-coded assumption that every option has the same multiplier or settlement style.
- No fabricated historical quote, expiry, or implied-volatility observation.
- No complete-project claim without mandatory derivative-hedge integration.
